## 3. Motivation

Retrieval-Augmented Generation systems often fail not because the language model cannot reason, but because the retriever fails to recover the necessary evidence.

This is especially important for **multi-hop question answering**, where a system may need more than one supporting passage. A retriever can look successful by retrieving one relevant passage, but still fail if it misses the second required passage.

HotpotQA is a good dataset for this project because it provides:

- natural language questions
- candidate context passages
- gold answers
- supporting facts
- question types such as bridge and comparison

The supporting facts allow us to directly evaluate whether a retrieval method recovered the necessary evidence.

---

## 4. Research Questions

1. How do BM25 and dense retrieval differ in recovering HotpotQA supporting evidence?
2. How often do retrieval methods recover all required evidence versus only partial evidence?
3. Do BM25 and dense retrieval fail differently on bridge questions and comparison questions?
4. When does dense retrieval succeed where BM25 fails?
5. When does BM25 succeed where dense retrieval fails?
6. What are the common failure modes in multi-hop evidence retrieval?
7. How does the BM25 vs dense gap change between the per-question distractor corpus and the pooled corpus?
8. Does reranking rescue missing evidence, or does it sometimes damage full evidence coverage?
9. Optional (fine-tuning extension): Does single-hop contrastive fine-tuning repair specific failure categories (e.g., lexical mismatch) while leaving structural multi-hop failures (e.g., first-hop-only) unfixed?

### Retrieval Unit

Use **paragraph-level passages** from the provided HotpotQA context.

Do not do sentence-level chunking or fixed-size chunking in the core project.

### Corpus Settings

Use **two corpus settings**, both built only from the candidate contexts provided inside HotpotQA examples:

1. **Pooled corpus (primary setting).** Merge the context paragraphs of all evaluation questions (e.g., 500 questions × ~10 paragraphs ≈ 5,000 paragraphs, deduplicated by title) into one shared retrieval corpus. Every question retrieves against this shared pool.
   - This is the main experimental setting for the report.
   - Rationale: with a shared pool, k = 2, 5, 10 are all meaningful, distractors are plentiful, and failure modes such as dense semantic drift and distractor entity failure can occur at realistic rates.
2. **Per-question distractor corpus (contrast setting).** Each question retrieves only against its own ~10 provided context paragraphs (the original HotpotQA distractor setting; this is what Week 1 implemented).
   - Keep this as a secondary condition for comparison.
   - Warning: in this setting Recall@10 is trivially 100% because the corpus has only ~10 paragraphs, and k = 5 may be near ceiling. Only k = 2 (and possibly k = 5) are informative here.

Comparing the two settings is itself an analysis dimension: how does the BM25 vs dense gap change as the candidate pool grows?

Do not retrieve from full Wikipedia. Full Wikipedia retrieval would add too much engineering complexity and make gold evidence matching harder. The pooled corpus is a controlled middle ground, not full-wiki retrieval.

### Gold Evidence

Use HotpotQA `supporting_facts` as gold evidence annotations, but keep the matching unit consistent with the retrieval unit.

HotpotQA supporting facts are usually represented as **title + sentence index**. Because the core project retrieves **paragraph-level passages**, the evaluator should map supporting facts to **gold evidence paragraphs**:

- Each retrieved passage should preserve its Wikipedia title.
- A retrieved passage counts as a gold evidence hit if its title matches a gold supporting-fact title.
- When sentence indices are available in the provided context, optionally verify that the matched paragraph contains the supporting sentence.
- Full Evidence Recall@k should be computed over the set of unique gold evidence paragraph titles, not over individual sentence indices.

This means the project evaluates paragraph-level evidence coverage, not sentence-level supporting fact extraction.

## 6. Core Methods

### 6.1 BM25 Lexical Retrieval

BM25 is the lexical baseline.

It ranks passages based on word overlap between the question and the candidate passages.

#### Why BM25 matters

BM25 is simple, fast, interpretable, and useful as a baseline. It often works well when the question and evidence share exact entity names or keywords.

#### Expected BM25 Strengths

- Strong exact entity matching
- Strong when question wording overlaps with evidence wording
- Easy to interpret
- Fast to run

#### Expected BM25 Weaknesses

- Struggles with paraphrases
- Struggles when the important evidence uses different wording
- May retrieve only the first-hop passage in bridge questions
- May miss the second entity in comparison questions

---

### 6.2 Dense Retrieval

Dense retrieval is the main method Xin wants to focus on.

It encodes questions and passages into vectors in a shared embedding space, then ranks passages by vector similarity.

#### Suggested Model

Start with:

```text
sentence-transformers/all-MiniLM-L6-v2
```

This model is lightweight, easy to run, and suitable for a course project.

Optional alternative:

```text
BAAI/bge-small-en-v1.5
```

Only switch models if the first pipeline is already stable.

#### Dense Retrieval Pipeline

1. Encode each question into a query embedding.
2. Encode each candidate passage into a passage embedding.
3. Compute cosine similarity or inner product between the query and each passage.
4. Rank passages by similarity.
5. Return top-k passages.

#### Why Dense Retrieval Is Interesting

Dense retrieval connects directly to representation learning:

- Questions and passages become vectors.
- Semantic similarity is approximated by vector similarity.
- Failures can be interpreted as representation-space failures.
- Dense retrieval may find semantically related passages even without exact word overlap.
- Dense retrieval may also retrieve semantically similar but non-evidential passages.

#### Expected Dense Retrieval Strengths

- Handles paraphrase better than BM25
- Can retrieve semantically related evidence
- Less dependent on exact word overlap
- More connected to modern neural retrieval and RAG

#### Expected Dense Retrieval Weaknesses

- Can suffer from semantic drift
- Can retrieve topically similar but non-evidential passages
- May over-focus on one entity and miss another
- May retrieve a passage that sounds relevant but does not support the answer

---

### 6.3 Dense Retrieval + Reranking

Reranking is the third core method, committed in the submitted proposal.

A reranker takes the top-N passages from dense retrieval and reorders them with a stronger relevance model. Use an off-the-shelf cross-encoder (e.g. `cross-encoder/ms-marco-MiniLM-L-6-v2`); no training is required.

Setup per corpus setting:

1. **Pooled corpus:** dense retriever returns top-50 candidates; the cross-encoder scores each (question, passage) pair and returns a new top-k ranking.
2. **Per-question corpus:** only ~10 candidates exist, so the reranker rescores all of them (candidate depth N = corpus size).

Core research question:

> Does reranking improve or harm full evidence coverage in multi-hop QA?

This is better than only asking whether reranking improves Any Evidence Recall@k.

#### Reranker Rescue

A reranker rescue happens when:

- Gold evidence is not in dense top-k before reranking.
- Gold evidence appears in top-k after reranking.

#### Reranker Damage

A reranker damage happens when:

- Gold evidence is in dense top-k before reranking.
- Gold evidence is pushed out of top-k after reranking.

#### Important Warning

The reranker cannot recover evidence that was never included in the first-stage retrieved candidate set. If the dense retriever does not retrieve a gold passage in top-N, the reranker cannot see it. In the pooled setting this makes the candidate depth N = 50 part of the experimental design; report dense Recall@50 alongside the reranked results so readers can see the reranker's ceiling.

## 8. Core Metrics

**AI-policy boundary for the evaluator.** The course AI policy singles out evaluation-heavy projects: the evaluation methodology and error analysis must remain the team's work. Because the evidence coverage metrics below (Full/Partial Evidence Recall, Any Evidence Recall, MRR) are part of this project's core intellectual contribution, the metric definitions and their core computation logic in `evaluator.py` must be hand-written by team members. Coding agents may generate only the surrounding infrastructure (CSV output, experiment runner, argument parsing, logging). This boundary must be stated in the AI Usage Declaration.

Report all metrics at:

```text
k = 2, 5, 10
```

These k values are useful because HotpotQA often requires at least two supporting evidence pieces.

Setting-specific caveat: in the per-question distractor setting (~10 candidate paragraphs), Recall@10 is trivially 100% and k = 5 may be near ceiling; treat k = 2 as the primary cutoff there and do not report k = 10. All three k values are meaningful in the pooled-corpus setting, which is the primary setting for the report.

### 8.1 Any Evidence Recall@k / Evidence Hit@k

Whether at least one mapped gold evidence paragraph appears in the top-k retrieved passages.

This metric is sometimes called Recall@k in retrieval reports, but in this project it should be defined explicitly as **any-evidence recall** or **evidence hit rate**, because it only requires one gold evidence paragraph to appear. It is not sufficient for multi-hop QA because retrieving only one supporting passage may not be enough.

### 8.2 Full Evidence Recall@k

Whether all required mapped gold evidence paragraphs appear in the top-k retrieved passages.

This is the most important metric for this project because multi-hop QA often requires all supporting evidence.

A method with high Any Evidence Recall@k but low Full Evidence Recall@k may be retrieving partially relevant evidence but still failing the actual multi-hop task.

### 8.3 Partial Evidence Recall@k

Whether some, but not all, required mapped gold evidence paragraphs appear in the top-k retrieved passages.

This captures cases where the retriever is partially successful, such as finding the first hop but missing the second hop.

### 8.4 MRR

Mean Reciprocal Rank measures how highly the first mapped gold evidence paragraph appears in the ranking.

It answers:

> If the method finds at least one mapped gold evidence paragraph, how early does it appear?

## 10. Failure Taxonomy

Use the same six core failure categories across the Scope document, Idea document, Weekly Todo plan, final report, and demo examples.

**Operational labeling rules (core hand-written contribution).** Each category must be assigned by explicit, reproducible decision rules implemented in `failure_analyzer.py`, then verified by manual inspection of representative cases. In particular, First-Hop-Only Failure and Missing Bridge Entity overlap (both are "found one hop, missed the other"); disambiguate them with a rule such as:

- If the *retrieved* gold paragraph's title entity appears verbatim (or near-verbatim) in the question, and the *missed* gold paragraph's entity does not → **first-hop-only failure**.
- If the missed gold paragraph's entity is reachable only through the content of the retrieved paragraph (the bridge) → **missing bridge entity**.

Writing, validating, and reporting agreement of these rules against ~20 manually labeled examples is part of the project's intellectual contribution and must be done by team members.

### 10.1 First-Hop-Only Failure

The retriever finds the passage related to the entity explicitly mentioned in the question but misses the second supporting passage.

This is especially common in bridge questions.

Typical pattern:

- One gold evidence paragraph is retrieved.
- The other gold evidence paragraph is missing.
- The retrieved evidence often corresponds to the first hop.

Report sentence:

> In bridge questions, both BM25 and dense retrieval often recovered the passage containing the explicitly mentioned entity but failed to retrieve the second-hop evidence needed to answer the question.

### 10.2 Missing Bridge Entity

The retriever fails to retrieve evidence about the bridge entity needed for the second hop.

Typical pattern:

- The first retrieved passage may mention or imply an intermediate bridge entity.
- The top-k results do not include the gold passage about that bridge entity.
- The model cannot complete the multi-hop chain even though one relevant passage was found.

Report sentence:

> Missing bridge entity failures occurred when retrieval found an initial relevant passage but failed to follow the intermediate entity needed to retrieve the second supporting passage.

### 10.3 Comparison Coverage Failure

The retriever retrieves evidence for only one side of a comparison question.

Typical pattern:

- The question compares entity A and entity B.
- Retrieved passages cover entity A but not entity B, or vice versa.
- Full Evidence Recall@k fails even though Partial Evidence Recall@k succeeds.

Report sentence:

> For comparison questions, partial retrieval was common because the retriever often covered only one of the compared entities, leaving the other side unsupported.

### 10.4 Lexical Mismatch

BM25 fails because the wording in the question does not overlap enough with the wording in the supporting evidence.

Typical pattern:

- Dense retrieval succeeds.
- BM25 fails.
- The evidence uses paraphrases, aliases, or related terms rather than exact question words.

Report sentence:

> BM25 failures were often caused by lexical mismatch, where the supporting passage expressed the relevant fact using different surface forms from the question.

### 10.5 Dense Semantic Drift

Dense retrieval finds a passage that is semantically related to the question but does not actually support the answer.

Typical pattern:

- Retrieved passage is topically similar.
- Retrieved passage shares broad semantic context.
- But it does not contain the required evidence.

Report sentence:

> Dense retrieval often retrieved passages that were semantically close to the question but not evidentially sufficient, suggesting that semantic similarity alone does not guarantee multi-hop evidence coverage.

### 10.6 Distractor Entity Failure

The retriever finds a passage about a similar entity or title, but not the correct supporting passage.

Typical pattern:

- Retrieved title looks similar to a gold title.
- Retrieved passage shares entity names or topic words.
- But it is not one of the required supporting evidence paragraphs.

Report sentence:

> Distractor entity failures occurred when the retriever was attracted to passages with similar names or overlapping topics, but those passages did not provide the required evidence.

### Reranker Rescue

The reranker improves retrieval by moving gold evidence into top-k.

Report sentence:

> Reranking rescued some examples by promoting gold evidence that was present in the dense candidate set but ranked too low by embedding similarity alone.

### Reranker Damage

The reranker hurts retrieval by pushing gold evidence out of top-k.

Report sentence:

> Reranking sometimes damaged full evidence coverage by over-prioritizing a single locally relevant passage while demoting the second supporting passage needed for multi-hop reasoning.

## 19. Final Scope Summary

Final version:

> This project focuses on evidence retrieval for multi-hop question answering on HotpotQA. We compare BM25 lexical retrieval, dense embedding-based retrieval, and dense retrieval with cross-encoder reranking using Any Evidence Recall@k / Evidence Hit@k, Full Evidence Recall@k, Partial Evidence Recall@k, and MRR, in two corpus settings: a pooled corpus built from all evaluation questions' context paragraphs (primary) and the original per-question distractor setting (contrast).
